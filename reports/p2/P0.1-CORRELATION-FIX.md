## 1. 问题 A · 跨会话工具耗时污染

### 根因

`apps/companion/renderer/monitor-projection.mjs` 旧实现：

```js
const lastTool = [...safeEvents].reverse().find(e => e.eventType === 'tool.end' || e.eventType === 'tool.fail');
const toolDurationMs = lastTool ? numeric(lastTool.durationMs) : null;
```

`safeEvents` 是渲染器全局缓存（包含所有会话），因此选中会话 A 时可能取到会话 B 的 `tool.end`，把 B 的 `durationMs/toolCallId` 填进 A 的投影。

### 修复

- 只从**选中会话**的事件中取工具结束事件：
  `selectedEvents = safeEvents.filter(e => e.sessionId === session.sessionId)`；
- **SessionManager 的结论优先**：`metrics.lastToolDurationMs / lastToolCallId / lastToolCorrelated` 由 session-manager 按会话维护；
- 只有 manager 没有结论（`lastToolCorrelated === undefined`）时，才在**选中会话缓存**中按 `toolCallId` 匹配 `tool.start` 重建；
- 无可靠关联时 `durationMs=null`、`correlated=false`。

## 2. 问题 B · 仅凭 toolCallId 非空就认定关联

### 根因

旧实现：

```js
const toolCorrelated = lastTool ? Boolean(clean(lastTool.toolCallId, 64)) : false;
```

只要事件带 `toolCallId` 就显示 `CORRELATED`，即使没有匹配的 `tool.start`，或 SessionManager 已判定未关联。

### 修复

- `toolCorrelated` 只来自显式状态：
  - `metrics.lastToolCorrelated === true`（SessionManager 已验证 start↔end 匹配）；或
  - manager 无结论时，在选中会话缓存中找到 **同 sessionId + 同 toolCallId** 的 `tool.start`；
- 单独 `tool.end` + `toolCallId` → `UNCORRELATED`、耗时 `—`；
- UI 的 `TOOL / DURATION` 使用 `active.lastToolCorrelated`，不再看 `toolCallId` 是否非空。

## 3. 附带修复

- `app.js#ingestEvents` 之前丢弃 `toolCallId/durationMs/errorCode/label`，导致即使后端有数据 UI 也看不到；现已保留，并把 `toolCallId` 纳入去重 key。
- `monitor-projection` 的 timeline 增加 `sessionId/toolCallId/durationMs/errorCode/confidence`，供事件详情使用。
- 新增 `selectedEventCount / selectedToolEventCount`，让 UI 能区分“没有工具事件”和“有工具事件但未关联”。

## 4. 回归测试（新增 3 项，已固化）

`tests/unit/correlation.test.mjs`：

1. **P0 regression A**：选中 codex 会话 A，缓存只有 claude 会话 B 的 `tool.start/end`（800 ms）→ A 的 `lastToolDurationMs=null`、`lastToolCallId=''`、`lastToolCorrelated=false`。
2. **P0 regression B**：选中会话只有一条 `tool.end` + `toolCallId`（无 `tool.start`）→ `UNCORRELATED`、耗时 `null`。
3. **P0 regression C**：SessionManager 明确返回 `lastToolCorrelated=false` 时，即使缓存中有同 ID 的 start/end，也保持 `false`、`null`（防止缓存“补出”伪造关联）。

另有既有断言：同会话 start(1000)/end(1600) → 600 ms；无 start → 不计算；schema 超长/错误类型拒绝。
