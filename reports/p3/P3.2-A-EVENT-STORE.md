# P3.2-A · Event Store / Replay

- 分支：`feat/paper-lab-p2`
- 实现：`packages/event-store`、`packages/event-bridge`、`scripts/haloflux.mjs`、renderer replay
- 结论：**PASS（本地持久化、查询、去重、保留/删除、确定性回放、真实回放录屏）**
- 历史边界：只覆盖 Event Store 启用之后的真实事件；启用前的内存缓存不会“复活”。

## 1. 方案比较（SQLite vs 分段 JSONL）

| 维度 | SQLite (`node:sqlite`) | 分段 JSONL |
|---|---|---|
| 查询 | 索引 `session_id/run_id/trace_id/timestamp`，按范围/Session/Trace 直接查 | 需自建倒排索引或全量扫描 |
| 去重 | `event_id PRIMARY KEY` + `INSERT OR IGNORE`，原子 | 需另存 seen-set，重启扫描重建 |
| 崩溃恢复 | WAL + `busy_timeout`，异常退出可恢复；`integrity_check` 可验 | 需处理半行/截断；尾部损坏易丢整段 |
| 并发 | 单写多读，WAL | 多进程追加需锁，易交错 |
| 安全删除 | `PRAGMA secure_delete=ON` + DELETE/VACUUM | 删除行可能残留块，不可靠 |
| 维护 | 无额外依赖（Node 24 内置）；迁移需版本化 | 文件切分/压缩简单，索引成本高 |
| 依赖影响 | Node >= 22.5 的 `node:sqlite`；不可用时 bridge 降级为不持久化 | 无依赖，但代码量更大 |

**选择 SQLite**：本项目需要按 Session/Run/Trace/时间的可复核查询、事件级去重和异常恢复；SQLite 的索引/WAL/主键更可靠。JSONL 保留为导出格式（`history --export`）。

## 2. 存储层

`packages/event-store/src/index.mjs`：

- 文件：`%LOCALAPPDATA%\HALOFLUX\events\haloflux-events.sqlite`（可用 `HALOFLUX_HOME` 隔离）；
- 表：`events(event_id PK, schema_version, timestamp, stored_at, host, session_id, run_id, trace_id, event_type, source, confidence, payload)`;
- 索引：timestamp、session、run、trace；
- 写入前用 `validateEvent()` 再校验一次，未知 metadata/凭据/正文不可入库；
- `appendMany()` 事务写入；重复 `eventId` 计为 duplicate，不重复计数；
- WAL、`synchronous=NORMAL`、`busy_timeout=3000`、`secure_delete=ON`；
- API：`append/appendMany/query/stats/pruneBefore/deleteSession/exportJsonl/integrityCheck/close`。

## 3. 查询与保留

```powershell
node scripts/haloflux.mjs history --limit 50
node scripts/haloflux.mjs history --session <id> --json
node scripts/haloflux.mjs history --session <id> --run <id> --trace <id> --from <ms> --to <ms>
node scripts/haloflux.mjs history --stats
node scripts/haloflux.mjs history --export D:\HALOFLUX-media\p3\history.jsonl
node scripts/haloflux.mjs history --delete-session <id>
node scripts/haloflux.mjs history --prune-days 30
```

- 默认保留 30 天（`HALOFLUX_EVENT_RETENTION_DAYS`），bridge 启动时裁剪；
- `--delete-session` + `VACUUM` 做安全删除；
- `--export` 输出脱敏后的原始事件 JSONL；
- `/v1/history`（GET，token 鉴权，limit ≤1000）与 `/v1/history/stats`。

## 4. 回放

- `?replay=<sessionId>`：renderer 从 `/v1/history` 拉取该会话事件，按 timestamp 排序；
- 顶部固定 **REPLAY** 条：会话、事件数/存储数、时钟、PAUSE/RESUME、STEP、0.5/1/2/4×、LIVE 返回；
- 回放只使用存储事件，不请求模型、不重跑工具；
- 确定性：`replay-engine.mjs` 的 `frameIndexAt/sessionAt/stepIndex` 只依赖事件时间戳，不受墙钟影响；
- 暂停、单步、倍速、`?at=N` 定位均有实现；`LIVE` 返回实时模式（清 query 后重载）。

## 5.1 持久性、兼容性与安全口径

- **WAL + `synchronous=NORMAL`**：进程崩溃/异常退出不会损坏数据库结构，已提交事务通常在 WAL 中可恢复；**系统断电/OS 崩溃时，最近已提交事务仍可能回滚**（SQLite 官方语义）。不得把它描述为绝对断电持久化；要更强保证需 `synchronous=FULL`（本项目未采用，以降低写延迟）。
- **Node 版本**：`node:sqlite` 在 Node 22.13 起无需实验启动标志；仓库 `engines` 已改为 `>=22.13.0`。更老 Node 上 bridge 会捕获 Event Store 初始化失败并降级为“不持久化”，不会阻塞事件链。
- **删除不是物理擦除**：`secure_delete=ON` + `DELETE` + `VACUUM` 只作用于 SQLite 文件；SSD 磨损均衡、文件系统快照、系统备份、云同步副本不在保证范围内。需要“不可恢复”时应使用全盘加密/安全擦除。
- **访问控制**：`/v1/history` 必须 Bearer token，和 `/v1/state` 同级；数据库位于当前用户 `%LOCALAPPDATA%`，依赖 Windows 用户 ACL，SQLite 本身未加密。token 文件权限仍是 P6 的 PARTIAL（Windows mode 0666），不宣称安全隔离。
- **备份/导出**：`history --export <file>` 导出脱敏事件 JSONL；数据库复制应在 bridge 停止后或 SQLite backup API 下进行，热复制可能得到不一致快照。
- **内容边界**：入库前再次 `validateEvent()`；metadata allowlist 之外的 prompt/正文/工具参数/结果/凭据/推理文本不能入库。

## 7. 限制（必须保留）

1. **历史只从启用 Event Store 起**；此前仅存在 30 条内存缓存的会话事件未被补录，不能声称完整历史。
2. `/v1/history` 默认最多 1000 条；超出需分页/导出。
3. SQLite 文件未加密（本地用户目录）；依赖 Windows 文件 ACL，token/凭据不入库。
4. 事件级 `runId` 仍依赖宿主提供；DSH 当前多数工具事件没有 `toolCallId`，回放中只能显示 `HOST_REPORTED`/`UNCORRELATED`，不能伪造配对。
5. 回放 UI 是“事件重放”，不还原当时的模型内部状态、GPU 或工具副作用。
