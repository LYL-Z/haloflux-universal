# P4.1-R · 性能归因与一致性门禁

- 基线：`0a3c9cc` + F-04/F-05 本地修复
- 结论：**PARTIAL（门禁未通过）**。F-04 快照一致性已修复，F-05 热路径已重构；但同口径 FPS 仍低于 P2.2，且回放 2500 条出现明显掉帧。**P4.2 不启动**，先解决性能归因。

## 1. F-04 数据快照

- 新增 `seq` 入库序列（SQLite 迁移 `user_version=2`）；事件 `timestamp` 与 `ingest seq` 严格分离。
- 查询改为 **snapshotSeq + afterSeq 游标**，不再依赖 `OFFSET`/`to=Date.now()`。
- 迟到但时间戳更早的事件获得更大的 seq，旧快照不可见；新快照才可见。
- 分页期间删除/清理会使 loaded < snapshot total，前端标 `PARTIAL REPLAY`。
- 测试：1205 条游标分页、late-old-timestamp、删除、2500/5000 前端分页、2500 真实 UI。

## 2. F-05 回放热路径

已实现：

- 事件只在加载时 `sortEvents()` 一次；
- `prepareReplay()` 预计算 timestamps、duration、density、checkpoints（每 128 条）；
- `indexAt()` 二分查找；`sessionAtIndex()` 从最近检查点增量应用（≤128 事件）；
- 时间带按 1024 像素桶聚合，不再每帧遍历全部事件；
- 移除 TRACE 面板在回放帧内的重复重绘（研究面板改为打开/切 tab 时刷新）。

Node 基准（`tests/evidence/p4/replay-bench.json`）：

| 事件数 | prepare | 2000 次 index | 200 次 seek | 单次 naive sessionAt | checkpoints |
|---|---|---|---|---|---|
| 652 | 2.3 ms | 0.93 ms | 7.5 ms | 0.69 ms | 6 |
| 2500 | 1.6 ms | 0.68 ms | 7.8 ms | 0.91 ms | 20 |
| 5000 | 3.5 ms | 0.25 ms | 10.4 ms | 1.13 ms | 40 |
| 20000 | **15.8 ms** | **0.21 ms** | **10.8 ms** | **3.30 ms** | 157 |

20k 条时单次 seek 约 0.054 ms；prepare 增加约 30 MB heap，仍可接受。

## 3. 同口径 FPS（1536×900，DPR 2.5，GPU）

| 模式 | FPS | P50 | P95 | 备注 |
|---|---|---|---|---|
| 纯视觉空载 | 30.4 | 33.3 | 41.7 | baseline |
| LIVE | 66.7 | 4.2 | 37.5 | rAF 超过显示刷新，不能当真实合成 FPS |
| LIVE + TRACE | 88.7 | 4.2 | 33.3 | 同上，测量口径异常 |
| REPLAY 652 + TRACE | 24.2 | 62.5 | 83.4 | at=600 |
| REPLAY 2500 + TRACE | **15.0** | 62.6 | 83.4 | at=2400 |
| REPLAY 2500 无 TRACE | 13.5 | 70.9 | 100.0 | 仍掉帧 |
| REPLAY 20000 + TRACE | 22.3 | 54.2 | 83.4 | at=19000 |

- LIVE 66/88 fps 与 60Hz 显示不一致，说明 p22-fps 的 rAF 统计在部分可见窗口模式下不可靠；不能据此宣称“超过 60fps”。
- 回放 652/2500/20000 都低于 30fps；2500 反而低于 20000，说明存在测量/渲染异常（窗口遮挡、DOM/Canvas 布局或 GC），不是简单线性规模问题。
- Page metrics：2500 prepare 2.5ms、首帧 31ms；20000 prepare 14.1ms、首帧 65.7ms。**prepare 不是主因**；掉帧发生在空闲渲染阶段 / 大 DOM/Canvas 合成。
- 结论：F-05 已消除重复排序和全量扫描，但未消除 FPS 回退；不能把 P4.1 标 PASS。

## 4. 与 P2.2 的对比

- P2.2：约 **38.6 fps**（1536×900，当时无 Timeband/TRACE/Replay）。
- P4.1：约 **28.5 fps**（同尺寸，P4 版本）。
- 回退约 26%，P95 41.7ms > 30fps 的 33.3ms。
- 这是不同提交/不同面板的真实差异，不能全部归因于新增画布，但足以阻止继续叠加粒子/弧带。

## 5. 门禁判定

| 条件 | 结果 |
|---|---|
| F-04 严格快照 / 游标 | **PASS** |
| F-05 只排序一次 / 二分 / 检查点 / 密度 | **PASS（代码与基准）** |
| 同口径 FPS 不低于 P2.2 | **FAIL**（28.5 vs 38.6） |
| 2500 回放 ≥24fps | **FAIL**（约 15fps） |
| P4.2 启动条件 | **不满足** |

## 6. 下一步（P4.1-R2）

1. 用 Chrome tracing / PerformanceObserver 定位 REPLAY 2500 的空间/布局热点（DOM 行数、Canvas 层、GC）。
2. 对 REPLAY 会话做 DOM 虚拟化（Feed/TRACE 只渲染可视行）。
3. 将时间带/Canvas 绘制与 200ms 回放循环解耦，避免整页 renderAll。
4. 复测 652/2500/5000/20000 同口径；通过后再做中央弧带、底部 Tool Waterfall、证据网络和束流映射。

**未启动 P4.2 大规模视觉深化**：这是遵守任务书“性能门禁优先”的要求，不是遗漏。
