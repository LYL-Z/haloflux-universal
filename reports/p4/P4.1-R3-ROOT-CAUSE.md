# P4.1-R3 · Root Cause

- Baseline: `e1e5642`
- Fixed workload: 2500 stored events, 1x replay, 1536×900 CSS viewport, DPR 2.5, GPU compositing, visible/focused window.
- Chrome trace: `tests/evidence/p4/trace-2500-play-lite.json.gz` (10s, 167,774 events).
- Raw trace SHA256 `7fdec640…ea53`; analysis `trace-2500-play-lite-analysis.json`.

## 1. Correct trace method

The first trace attempt used all timeline categories and produced only 1.5s of main-thread data; that trace is retained but is not used for attribution. The reproducible trace uses:

```
devtools.timeline,cc,gpu
```

and is started after replay paging completes. Main-thread attribution is computed per `CrRendererMain` thread, not by summing overlapping durations from every process (the old analyzer did that and was invalid).

## 2. Measured attribution (2500 replay, 10s)

| Stage | Time | Share / note |
|---|---|---|
| CrRendererMain busy | **2,578 ms** | **26%** of 10.0s; no `RunTask` >50 ms |
| JS (`FunctionCall`, `EvaluateScript`, `RunTask`) | 699 ms | 27% of main-thread busy |
| Animation (`FireAnimationFrame`) | 593 ms | 23% of main-thread busy; 1,076 frames |
| `ProxyMain::BeginMainFrame` | 770 ms | commit/pipeline handoff |
| Layout | 103 ms | 4% of busy |
| Paint | 67 ms | 3% of busy |
| GC | 26 ms | negligible |
| GPU raster | 2,996 `DoRasterCHROMIUM` tasks | 8,975 ms summed; max 43 ms |
| GPU command buffer | ~9.8s summed over 10s | overlapping; queue/raster backpressure |

The main thread is **not saturated** and has no long tasks >50ms. The remaining frame time is dominated by the visual/compositor pipeline: dense canvas layers are rasterized 2,996 times in 10 seconds, and GPU command-buffer flushes overlap the whole window.

## 3. Isolated modes

| Mode | CrRendererMain busy | JS | Composite | Interpretation |
|---|---|---|---|---|
| visual-only mock | 1,958 ms / 10s (20%) | 734 ms | 20 ms | baseline animation |
| replay 2500 paused | 4,322 ms / 10s (43%) | 552 ms | 1,149 ms | initial layer commit (582 ms) contaminates this sample |
| replay 2500 playing (lite) | 2,578 ms / 10s (26%) | 699 ms | — | steady playback; no long tasks |

The paused trace's 43% is not steady-state: one initial `Commit`/`UpdateLayer` pair costs ~582 ms, concentrated at load. This explains why short/early samples can show ~15 FPS while a controlled 30s foreground measurement shows ~30 FPS.

## 4. Root causes (confirmed vs suspected)

Confirmed:

1. **GPU raster/compositor work is the largest frame-budget consumer** for the dense visual; 2,996 raster decodes and ~9.8s overlapping command-buffer flush in 10s.
2. **Main-thread animation/commit is second**: 26% busy, `FireAnimationFrame` 593ms, `BeginMainFrame` 770ms; still below one full core.
3. **Initial load/layer commit spike** (~582ms) is a separate, one-off cost that can corrupt short FPS windows; not steady-state playback.

Suspected (not proven as the dominant cause):

- Feed DOM rebuild (`renderLabMonitor`) and canvas backing-store churn. Phase instrumentation shows `renderLabMonitor` ≈1.44ms/update and canvases ≈1.17ms/update, too small to explain a 15–18 FPS steady state by themselves.
- Canvas/GPU memory pressure from DPR 2.5 backing stores; trace shows raster volume, not a specific canvas name.

## 5. Conclusion

The old “15 FPS” claim mixed **initial commit/load spikes, paused-mode sampling and steady playback**. Under a controlled foreground 30s run, 2500/20000 replay now measure ~29–30 FPS. The remaining visual headroom is primarily GPU raster/composite, not JavaScript algorithmic cost.
